## 二、切片和验收

### A. 拆模块，加高德接口（重构，所有现有测试原样通过）

- **按职责拆成几个模块**，名字由执行代理定，大致是：
  - 地点和高德客户端；
  - 行程模型和读配置；
  - 求解；打车安排；行程表；报告；
  - TOML 读写。
  - **`carpool.py` 保留为门面**：原来的 `carpool.X` 都还能用，命令行 `python3 carpool.py trip.toml` 照常工作。模块之间单向依赖，不能互相引用成环。
- **高德接口**：用 `typing.Protocol` 写一个，比如 `AmapLike`，列出计算核心和 `service.py` 实际调用的全部方法和属性，每个写一句「用来做什么、对应高德哪个接口」。
  - 加测试：四个实现都满足这个接口；计算核心和 `service.py` 里对高德客户端调用的方法，全都在接口里。
  - 接口的说明里加一张表，列出计算用到的高德服务类别、对应的 Web 服务接口和额度类别（地点搜索，或者路线和测距），供以后评估浏览器直接调用、JS API 或其他数据源时用。
- **网页版要能加载新模块**：`web/pyworker.js` 的加载清单、`web/build.mjs` 复制到 `dist/py/` 的清单都要更新。最好改成由一处清单生成，免得以后漏加。
- **重点风险：模块级的可变全局**。比如 `carpool.progress`：`browser.py` 给它赋值，`report()` 读它。拆到别的模块以后，给门面赋值就不起作用了。要找出所有 `carpool.<名字> = …` 的赋值，包括测试里的替换，逐个保证拆分后仍然生效，并加测试。
- **验收**：
  - 金标准 `GoldenTest` 逐字节通过，规则快照通过，`RULES_VERSION` 不变；
  - `npm test`、`npm run build` 通过；
  - `npm run e2e` 通过，这一项会在试玩模式下验证网页版加载 Python 模块；
  - 命令行 `python3 carpool.py` 用一份临时配置配合 `FakeAmap` 或 `TryAmap` 能跑出报告，不调用真实高德；
  - 汇报每个模块的行数和职责、依赖图，以及高德接口的方法清单。

## 三、风险和边界

- **Pyodide 的文件加载**：新模块漏加，网页版会在导入时出错。端到端测试的试玩场景会发现这个问题。
- **pickle 和缓存**：如果有地方按模块路径序列化对象，拆分后路径会变。执行代理要查一遍，现在看没有。
- **不改的东西**：计算结果、报告和方案页的文字、Worker 接口、编辑页。
