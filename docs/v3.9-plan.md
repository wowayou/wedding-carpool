分工：主代理出方案和验收，Sonnet 子代理执行。**这一版只做重构，用户看到的东西一个字都不变**，所以不出预览页。发布照常要等站长同意。

## 已定的决定（2026-10-09）

- 站长说「v3.9 开工」。范围按 [v3.8 计划](v3.8-plan.md) 第三节的路线：统一「行程表」，让报告、方案页、界面三处都只读它，`share.py` 不再自己推算时刻。

## 一、现在的问题（2026-10-09 核对代码）

一个方案定下来以后，「谁几点出发、几点到哪、等多久、打车几点汇合」由**三处各自推算**：

| 输出 | 去程 | 返程 |
|---|---|---|
| 报告（Markdown） | `carpool.describe`：`pickup_ready` → `route_schedule`，打车用 `taxi_cars` | `carpool.describe_back`：`leave_of`、`stop_times`、`taxi_cars`，等待时间就地相减 |
| 方案页（HTML） | `share._outbound`：同样调 `pickup_ready`、`route_schedule`、`taxi_cars`，乘客的上车、到达时刻再取一遍；车次的发车、到站时刻用 `train_times` 自己拆 | `share._return_section`：同样调 `leave_of`、`stop_times`、`taxi_cars`，每个乘客再调一次 `stop_times`，等待时间再减一遍 |
| 界面数据 | `service.plan_payload`：`pickup_ready`、`route_schedule`，只取出发时刻 | `service._back_payload`：`leave_of` |

后果：
- **改一条时刻规则，要同步改三处**。v3.7 加个人离场时间，就是三处都改了一遍。漏改一处，报告和方案页就对不上，而且现有测试多半发现不了。
- `share.py` 依赖 `carpool` 的 7 个推算时刻的函数：`pickup_ready`、`route_schedule`、`stop_times`、`taxi_cars`、`leave_of`、`train_times`，还有 `OUT`。这是两个模块之间最紧的耦合。

## 二、目标

- **行程表**：求解之后，每个方案（去程、返程各自）一次算出一份行程表，里面有：
  - **每辆车**：车主、出发时刻（去程按接人倒推，不知道车次时刻就没有；返程是车主的离场时间）、按顺序的各个停靠点（点、时刻、在这里上车或下车的人）、到达时刻（去程到目的地，返程到家）、全程和多绕的分钟数；
  - **每个坐车的人**：坐谁的车、在哪上车、上车时刻、到达时刻、要坐的车次及发车和到站时刻、返程等车主多久；
  - **每辆出租**：站、同车的人、汇合或出发时刻、车程、哪些人没填车次、返程每人等多久；
  - **待安排的人**：返程写离场时间。
- **三处输出都只读行程表**。各自只负责「怎么写出来」：文字、HTML、JSON。推算时刻的函数只在生成行程表时用到。
- **只算一次**：一次计算生成的行程表，报告、方案页、界面数据共用同一份，不重复推算。
- **输出一个字都不变**：报告、方案页 HTML、界面 JSON 改前改后逐字节相同。规则快照不动，`RULES_VERSION` 不变。

## 三、切片和验收

按顺序做，前一片合并后再开下一片。

### A. 先把现在的输出固定成「金标准」（不改任何业务代码）

- 选一组场景，尽量复用 `test_carpool.py` 里现有的 `FakeAmap` 场景。要覆盖到 `describe`、`describe_back`、`_outbound`、`_return_section`、`plan_payload`、`_back_payload` 的每个分支：
  - 去程：有车次、没车次、到家附近接、同行多人、打车拼车（省钱和最快两种）、有人待安排；
  - 返程：车主和乘客离场时间不同（乘客要等）、打车组里有人要等、赶不上车次被列为待安排；
  - 只规划去程、只规划返程、两段都有；方案页的几种去程和返程组合。
- 每个场景把三样输出存成文件，放在 `tests/golden/`：报告 Markdown、方案页 HTML（生成时间和过期日期固定）、`plan_payload` 的 JSON（排好键）。
- 新测试逐字节比对。不一致时报出是哪个场景、哪个文件，并给出看差异的命令。重新生成要显式加参数或设环境变量，平时跑测试不会自动覆盖。
- 用 Python 自带的 `trace` 模块，或者手工核对，确认上面六个函数的分支都被这些场景走到了，在汇报里列出覆盖情况。
- **验收**：金标准文件由**当前 main 的代码**生成；`npm test` 全过。

### B. 行程表（重构，金标准必须原样通过）

- 在 `carpool.py` 里新增一节「行程表」：几个数据类，加上生成函数，比如 `timeline(plan, trip, T, leg)`。名字和结构由执行代理定，要简单。v3.11 拆模块时，这一节会整体搬进单独的模块，所以不要和别的部分交叉引用。
- 时刻推算集中到这里：`pickup_ready`、`route_schedule`、`stop_times`、`taxi_cars`、`leave_of`、`arrival_at`、`back_deadline` 怎么组合，等待时间怎么算，车次的发车和到站时刻怎么拆。原函数如果求解时还要用，就保留，比如 `taxi_cars`、`leave_of`、`back_deadline` 在选站和分车时也用到；但输出端不再直接调用它们。
- **只算一次**：`service.compute` 在求解之后生成全部方案的行程表，放进 state；`plan_payload`、`share.render_share`、`carpool.render` 都从这里取。命令行（`carpool.run`）也走同一个生成函数。
- `describe`、`describe_back`、`share._outbound`、`share._return_section`、`service.plan_payload`、`service._back_payload` 改成只读行程表。
- **加测试守住**：
  - 静态检查 `share.py` 和 `service.py` 里不再出现上面那几个推算时刻的函数名；
  - 报告、方案页、界面里同一个人的同一个时刻来自同一个对象，比如改行程表里的一个时刻，三处输出一起变。
- **验收**：
  - 金标准逐字节通过、规则快照通过、`npm test` 全过、`npm run build` 通过；
  - Playwright 在本地 `wrangler dev` 的试玩页上算方案、生成方案页，控制台没有报错；
  - 汇报 `share.py` 对 `carpool` 的依赖前后各有哪些名字。

## 四、风险和边界

- **浮点和取整**：现在三处各自取整、格式化。行程表里存原始分钟数，取整和格式化留在各输出端，否则金标准会差一分钟。
- **INF 和 None**：「不知道时刻」现在有的用 `None`，有的用 `INF`。行程表统一用 `None` 表示不知道；需要 `INF` 参与比较的地方，在生成函数里处理。输出端看到的值和现在相同。
- **方案页的组合**：去程方案 i 加返程方案 j，各读各的行程表，互不影响。
- 不改 `ui.html`。界面数据的 JSON 格式不变，要加字段留到以后。
